    CLI Reference¶

    Use the CLI to create tickets, control runs, and inspect results: kontora <command> [flags] [arguments].

    New to Kontora? Follow Getting started for your first ticket and run. Run kontora help for the command list.

    Common flags¶

    Flag Applies to Description
    --config PATH every command that reads the config Path to the config file. Defaults to $KONTORA_CONFIG, then ./.kontora/config.yaml, then $XDG_CONFIG_HOME/kontora/config.yaml, then ~/.config/kontora/config.yaml.
    --tickets-dir PATH every command that reads the local ticket store Overrides tickets_dir. The highest precedence there is: above $KONTORA_TICKETS_DIR, $TICKETS_DIR and the config file. Ignored in remote mode, where the daemon owns the store.
    --url URL every command that can drive a daemon Remote daemon URL. A non-empty value switches the command into remote mode. Defaults to $KONTORA_URL.
    --token TOKEN the same commands Bearer token for the remote daemon. Defaults to $KONTORA_TOKEN.

    Put flags before the ticket ID, title, or other positional arguments. Both -flag and --flag work.

    Ticket IDs¶

    Commands that take a TICKET_ID accept a unique prefix, except for result, which requires the exact invocation ticket ID. For example, kontora view kon-q finds kon-q88f. A prefix that matches more than one ticket is an error naming every match, rather than a guess.

    Environment variables¶

    Variable Read by Description
    KONTORA_CONFIG every command Config file path. The daemon exports it to the agents it spawns, so kontora note inside a worktree writes to the daemon's own config.
    KONTORA_URL client commands Remote daemon URL; setting it turns on remote mode.
    KONTORA_TOKEN client commands Bearer token sent to the remote daemon.
    KONTORA_WEB_TOKEN kontora start only Overrides web.token on the daemon side, so a deployment can inject the secret instead of writing it into the config file.
    KONTORA_TICKETS_DIR every command that reads the local ticket store Overrides tickets_dir from the config file. The daemon exports its resolved value to the agents it spawns.
    TICKETS_DIR the same commands Compatibility alias for the standalone ticket CLI. Read only when KONTORA_TICKETS_DIR is unset or blank.
    KONTORA_AGENT kontora note The configured name of the agent the run belongs to. The daemon exports it to the agents it spawns, so an agent's own note is signed with the name it runs as. --author outranks it.
    KONTORA_STAGE agents and hooks The stage the run belongs to.
    KONTORA_TICKET_ID stage agents and lifecycle commands Current ticket; prevents an agent from changing its own lifecycle.
    KONTORA_RESULT_VERSION result Bound result protocol version: 1 for legacy supervised runs, 2 for graph agent nodes.
    KONTORA_WORKFLOW_EXECUTION_ID graph results Current workflow execution identity.
    KONTORA_NODE_VISIT_ID graph results Current executable visit identity, retained on retry.
    KONTORA_DEFINITION_FINGERPRINT graph results Bound effective workflow definition fingerprint.
    KONTORA_RESULT_VERDICTS graph results JSON array of this node's declared verdicts.
    KONTORA_INVOCATION_ID result Identity of this physical invocation; changes on retry and resume-to-fresh fallback.
    KONTORA_RESULT_TICKET result Exact ticket identity bound to this invocation.
    KONTORA_RESULT_STAGE result Stage identity bound to this invocation.
    KONTORA_RESULT_FILE result Absolute path to the immutable per-invocation result artifact.
    KONTORA_PAGER view, logs, activity Pager command, split on whitespace the way $EDITOR is. Used only when stdout is a terminal, so a redirect or a pipe is never paged. Set but blank turns paging off.
    TICKET_PAGER the same commands Read when KONTORA_PAGER is unset, so a ticket user's setting carries over.
    PAGER the same commands The last fallback before the config's pager.

    The tickets dir is resolved --tickets-dir → $KONTORA_TICKETS_DIR → $TICKETS_DIR → tickets_dir: → ~/.kontora/tickets, and the pager $KONTORA_PAGER → $TICKET_PAGER → $PAGER → pager: → none.

    Note that unlike every other setting, the environment beats the config file for the tickets dir. A stray export therefore changes which store every command reads, and a daemon that cannot see the variable — one started by launchd or systemd, which pass a minimal environment — keeps reading the file. kontora doctor names the source that won and warns when the two disagree.

    Tickets¶

    kontora ls¶

    Lists tickets. On a terminal with no flags it opens the kanban TUI; any filter, --json, --static, --closed or --archived makes it print instead. Done, cancelled and legacy closed tickets are hidden unless --closed is given; archived ones need --archived.

    Flag Description
    --closed Include done, cancelled and legacy closed tickets.
    --archived Include archived tickets.
    --status STATUS Only tickets in this status. Naming a hidden status shows it, so --status done needs no --closed and --status archived no --archived.
    --project NAME Only tickets for this configured project.
    --path PATH Only tickets for this repository path.
    --ready Only todo kontora tickets whose dependencies are all closed.
    --blocked Only todo kontora tickets waiting on a dependency.
    --limit N Print at most N tickets.
    --json Print JSON instead of a table.
    --static Print the static table even on a terminal.

    --ready and --blocked select opposite sets and cannot be combined; passing both exits non-zero. Both follow scheduler order, oldest created first. Every other listing keeps the board's order: by status, then most recently touched.

    The static table has ID, status, title, project, stage, agent, and the ids blocking the ticket.

    --json prints an array of objects with id, title, status, kontora, path, project, pipeline, stage, agent, created_at, started_at, completed_at, deps, links, parent, kind, epic_execution, child_order, branch, base_branch, ready and blockers. epic_execution: "agent" identifies an activated supervisor. child_order is stored display order, not membership; use each child's parent to find members. It never carries the ticket body; kontora view --body is what prints that. deps, links and blockers are always arrays, and an empty result is [], so a script can iterate without a nil check.

    The local TUI uses the daemon API only after verifying that its advertised tickets_dir identifies the requested local directory. Requested paths can be relative, contain ~, or use symlinks. Automatic discovery accepts only loopback addresses, localhost, or wildcard addresses normalized to loopback. It does not use proxies or follow redirects.

    If verification fails, the TUI displays the requested files with a diagnostic. Ticket actions and terminal attachment are disabled. Older daemons without directory identity also use file mode. With a verified daemon, attachment additionally requires its advertised tmux session and socket. The TUI passes that socket with tmux -S, rather than inheriting the client's server selection. Socket discovery never starts a tmux server. The TUI refreshes attachment identity every two seconds, so sessions created after startup become attachable without restarting the TUI.

    Verification applies to the initial connection. It does not bind a long-lived TUI to one daemon across server replacement at the same address.

    Explicit remote mode (--url or KONTORA_URL) does not require local directory identity. Remote mode asks the daemon for every ticket, including the hidden statuses, and applies the same filters locally, so a flag means the same thing on both sides.

    kontora search [flags] QUERY¶

    Matches QUERY against every ticket file in tickets_dir, frontmatter block and body alike, and prints the matching lines grouped by ticket. Every status is searched, archived included, so this is the only command that can find a closed ticket by what is written in it. Local only: it reads the files directly and needs no daemon.

    QUERY is a Go regular expression. Case follows ripgrep's smart-case rule: an all-lowercase query matches case-insensitively, and a query holding an uppercase letter matches case-sensitively. A query that starts with - needs -- in front of it, as in kontora search -- -race.

    Because the match runs over the raw markdown, frontmatter keys kontora does not own are searchable too: kontora search 'priority: 2' finds them. The one thing not in the file is the project name, which comes from the config; a query matching a configured project name reports that project's tickets with a synthetic project line.

    Flag Description
    -i Case-insensitive match, overriding smart-case.
    -s Case-sensitive match, overriding smart-case.
    -F Treat the query as a literal string, not a regex.
    -l Print matching ticket IDs only, one per line, for piping into xargs.
    -m N Show at most N matching lines per ticket. Defaults to 5; 0 shows all.
    --body Search the markdown body only, skipping the frontmatter. Project names are not matched either: a project name is in neither.
    --json Print a JSON array of results instead of the grouped listing.
    --status STATUS Only search tickets with this status. A status that is neither built in nor configured is a warning on stderr, since a ticket written by another tool may carry any status.
    --project NAME Only search tickets for this configured project. An unknown name is an error.
    --path PATH The same, by repository path.
    --pipeline NAME Only search tickets for this pipeline. An unknown name is an error.
    --agent NAME Only search tickets carrying this agent override. An unknown name is an error.

    Each --json object holds id, title, status, stage, pipeline, agent, path, project, file, total and a matches array of {line, field, text, start, end}. line is the 1-based file line, 0 for the synthetic project match; start and end are byte offsets of the match inside text; total counts every match found, the project match included, so it exceeds len(matches) when -m cut them. -m never cuts the project match, which is the reason the ticket is in the results at all.

    -l and --json, and -i and -s, cannot be combined. The exit status is 0 whether or not anything matched, unlike grep: a script that needs the difference reads the output, for example test -n "$(kontora search -l worktree)".

    A ticket whose frontmatter cannot be parsed is reported on stderr with the count and the parse error, rather than dropped, so a malformed ticket does not silently disappear from a search that should have found it. Only files the query matches are parsed, so a malformed ticket the query is nowhere in stays quiet.

    ^ and $ are line anchors, so kontora search '^status: done' matches the frontmatter line rather than the whole file. Note that a query matching a configured project name also matches the kontora: true marker line in every ticket kontora manages, so it returns most of the store.

    kontora new [flags] TITLE¶

    Creates a ticket and prints its ID. Locally, omitting --path with --parent EPIC_ID uses the resolved parent epic's stored path. Without --parent, it uses the current git root. An explicit --path always wins. Remote mode still requires --path on the daemon host, even with --parent. API creation (POST /api/tickets) likewise requires path.

    Flag Description
    --path PATH Repository the ticket works in.
    --pipeline NAME Explicit pipeline, or none to skip all pipeline defaults and run standalone.
    --agent NAME Agent to use, or none to skip the project default.
    --notify STATUSES Comma-separated statuses. Omit to inherit the project's list; "" or none skips it. Epics do not inherit.
    --notify-channels NAMES Comma-separated channel names; none silences delivery.
    --branch NAME Work branch name. Defaults to <branch_prefix>/<title-slug>-<ticket-id>. With branch_naming.mode: off or a title that yields no slug, uses <branch_prefix>/<ticket-id>.
    --base-branch NAME Branch the work branch starts from. Defaults to the repository's default branch.
    --status STATUS open or todo. Defaults to todo.
    --kind KIND epic for a ticket that groups others. See Epics.
    --parent TICKET_ID Epic to file the new ticket under. Takes an id or a unique prefix, and is refused when it names no ticket or a ticket that is not an epic.
    --at TIME Schedule pickup for an instant: RFC 3339 (2099-09-01T09:00:00+02:00) or a local wall time ("2099-09-01 09:00").
    --after DURATION Schedule pickup this long from now, e.g. 90m, 24h, 3d, 2w.
    --description-file PATH Read the markdown that follows the generated # <title> heading from a file, or - for stdin.
    --quiet Print only the new ticket ID.

    The ticket file is written once, complete. A ticket created with --status open is therefore never visible as todo, so a daemon with auto_pick_up: true watching the directory cannot claim it before you finish editing it. --status open also skips the repository check creation normally runs, because an open ticket is not ready to run.

    For ordinary tickets, an explicit --pipeline wins. Otherwise Kontora uses the matching project's epic_child_pipeline for a child of any actual epic, passive or agent. It then falls back to the project's pipeline, global default_pipeline, and standalone execution. A missing or ordinary-ticket parent never qualifies for the child default. Project matching uses the selected path and remains lexical. --pipeline none does not change independent agent resolution.

    --kind epic creates a passive epic in open and skips the repository check. It accepts --agent without starting it. It cannot be combined with a pipeline, --parent, --at, --after or --status todo. Creation never starts a supervisor. The daemon derives passive status from children. Use kontora run EPIC_ID to activate a supervisor; see Epics.

    --at and --after create the ticket open with a scheduled_at stamp, in the same single write. They cannot be combined with each other, or with --status todo: the schedule is what moves the ticket to todo. An --at already in the past is refused, and a scheduled ticket has its repository checked at creation the way a todo one does, because nobody is watching when it starts.

    kontora view TICKET_ID¶

    Prints the ticket's status, pipeline position, effective agent, and body. A ticket's agent override takes precedence over the pipeline stage's agent.

    Flag Description
    --body Print only the stored markdown body: no metadata, no styling, no synthesized relation sections.
    --notes Print stored markdown from the ## Notes heading through the end of the body, including later sections.
    --last N Print from the start of the Nth-last note through the end of the body. Requires a positive integer and implies --notes. 
    kontora view TICKET_ID
kontora view --body TICKET_ID
kontora view --notes TICKET_ID
kontora view --last 5 TICKET_ID

    Legacy notes without bylines also count. If N exceeds the note count, --last N prints the whole Notes section, including its ## Notes heading. Both note views retain trailing sections, including old review text outside Notes. If the ticket has no Notes section, both print nothing and exit 0. Combining --body with --notes or --last fails with a usage error.

    --body prints exactly what the file holds after the closing frontmatter delimiter, which is what kontora update --body-file writes back. Reading a body out, editing it, and writing it back changes nothing else in the ticket.

    --notes is for a reader that needs the history, not the plan. A long ticket's full output can exceed an agent's tool-output limit; the notes alone are usually much shorter.

    The default output goes through the pager when one is set and stdout is a terminal. --body, --notes and --last never use a pager, in local or remote mode.

    kontora edit TICKET_ID¶

    Opens the ticket file in $EDITOR. Local only.

    kontora update TICKET_ID [flags]¶

    Changes frontmatter fields or the body of an existing ticket. At least one flag is required. Passing an empty value, or none where noted, clears the field.

    Flag Description
    --body-file PATH Replace the body from a file, or - for stdin.
    --pipeline NAME Set the pipeline ("" or none clears it).
    --path PATH Set the repository path.
    --agent NAME Set the agent override ("" or none clears it).
    --notify STATUSES Set comma-separated statuses ("" or none removes the field).
    --notify-channels NAMES Set comma-separated channels ("" removes the override; none silences delivery).
    --branch NAME Set the work branch ("" clears it).
    --base-branch NAME Set the base branch ("" clears it).

    A passive epic's brief is editable in every status. An activated agent epic uses ordinary edit restrictions while running or terminal. Epics never accept a pipeline.

    kontora delete TICKET_ID -f¶

    Deletes the ticket's markdown file. -f or --yes is required. The worktree is not cleaned up; cancel the ticket first if you want the normal cleanup path.

    Deleting an epic locally leaves its children's parent references unchanged. Use remote mode, the dashboard, or the API to clear those references during deletion. No child ticket is deleted.

    kontora init TICKET_ID [flags]¶

    Marks an existing ticket file kontora: true so the daemon will run it. Without flags it prompts for the missing fields; naming them makes the command non-interactive, which is what a script or a coding agent needs.

    Flag Description
    --path PATH Repository path. Required when the frontmatter has none.
    --pipeline NAME Pipeline to run, or none for a standalone ticket.
    --agent NAME Agent to use, or none to skip the project default.
    --stage NAME Starting legacy stage. Graphs must start at their configured entry node; arbitrary starting nodes are refused.
    --status STATUS open or todo. Defaults to asking.

    For ordinary tickets, pipeline precedence is explicit request, stored nonempty pipeline, project epic_child_pipeline for an actual epic child, project pipeline, global default_pipeline. The child default applies under passive and agent epics. Initialization resolves actual membership before filling a blank pipeline. Agent defaults remain independent.

    If the pipeline remains blank, local init opens the pipeline picker, or errors if no pipelines are configured. Pass --pipeline none for standalone execution.

    --pipeline none leaves a blank pipeline for this request. Kontora does not store the opt-out; a later initialization can fill the blank unless you pass none again. Existing assignments are not migrated after config, parent or detail-path changes. Operators must retarget stored pipelines explicitly with kontora update --pipeline.

    For an epic, explicit --status todo activates a supervisor and validates that every child uses the epic's repository. Omit --pipeline and --stage; use --agent to select the supervisor. Passive epic initialization without explicit --status todo is refused. Starting an epic through local init requires a running daemon, so it queues the supervisor even with auto_pick_up: false.

    For ordinary tickets in remote mode, --pipeline and --path are both required, because the pickers cannot run over HTTP. --status is sent; --stage is not, so the remote form starts at the legacy pipeline's first stage or the graph's entry. Initializing a scheduled ticket with --status todo queues it now and drops the timestamp; --status open keeps it.

    Lifecycle¶

    kontora run TICKET_ID¶

    Enqueues an open or todo ticket. Needs a running daemon. When the ticket's dependencies are not all closed it reports it as blocked, naming them, rather than saying it was queued: the daemon will not pick it up until they close. See dependency-aware scheduling.

    On a passive epic, run explicitly activates a supervisor and writes epic_execution: agent. Activation requires one Git repository for the epic and every child. The supervisor runs standalone without a pipeline, using its own branch and worktree; children retain theirs. Successful completion goes to human_review.

    Supervisor prompts prohibit changing, clearing or replacing child pipelines and editing pipeline definitions, stage definitions or project pipeline defaults. Supervisors must create children without --pipeline. They must not bypass workflows through init, stage skipping, direct file edits or pause/retry sequences. If work conflicts with their authority, supervisors must report the conflict and leave that work unstarted pending an operator decision. These are prompt instructions, not runtime enforcement; ordinary operator commands remain available. Pipeline defaults do not grant permission to commit or publish. See Epics for review, Git and approval limits, and upgrade requirements.

    kontora schedule TICKET_ID¶

    Sets or clears the time the daemon moves an open ticket to todo. Needs a running daemon. See scheduled pickup.

    Flag Description
    --at TIME An instant: RFC 3339 (2099-09-01T09:00:00+02:00) or a local wall time ("2099-09-01 09:00"), read in the calling machine's zone. A date with no time is refused, because which midnight it means depends on the reader's zone. Stored normalized to UTC. An instant already in the past is refused.
    --after DURATION A duration from now, e.g. 90m, 24h, 3d or 2w. Go's duration units plus d (24 hours) and w (168 hours); composite forms such as 1w2d3h work. Resolved on the calling machine's clock.
    --clear Remove the schedule. The ticket stays open.

    Exactly one of the three is required. Scheduling a todo ticket returns it to open and drops it from the ready queue; the timestamp is what puts it back. Setting a schedule is refused on a running, closed or archived ticket, and while a Plannotator session or a pending annotation owns the ticket. --clear is refused only while the ticket is running, so a timestamp left behind anywhere can be removed without editing the file.

    kontora run on a scheduled ticket clears the timestamp and queues it now, in one write.

    kontora pause TICKET_ID¶

    Stops a running ticket and parks it in paused. A ticket that already closed cannot be paused; use retry to reopen it. On an agent epic, pause stops only the supervisor. Running children continue.

    kontora retry TICKET_ID¶

    For legacy execution, resets an initialized ticket to todo with the attempt counter cleared. For a graph, repeats the same executable visit with a fresh invocation, preserving execution identity, visit identity and loop counts. Graph retry at an end node is refused; use workflow restart for a new traversal. Refused for tickets in in_progress, todo, or archived, and for passive epics.

    Local mode only updates the ticket file. With auto_pick_up: false, follow retry with kontora run TICKET_ID. Remote mode and dashboard/API retry queue dependency-ready work even with automatic pickup off.

    Queueing does not mean the run has started. Before preparing a replacement workspace, the daemon checks for leftover tmux windows. Duplicate windows or uncertain cleanup prevent replacement and preserve execution reservations. Inspect last_error and the prior window before retrying again.

    kontora workflow-restart TICKET_ID¶

    Requires a running daemon.

    kontora workflow-restart TICKET_ID

    workflow-restart starts a new execution at the graph's entry. It resets visit and loop counters, but retains history, sidecar numbering and the existing worktree. It does not undo shell effects or discard files. Stop execution and resolve outstanding recovery before restarting. A changed definition requires inspection and an explicit new execution, not silent continuation.

    kontora workflow-recover TICKET_ID¶

    Requires a running daemon. Put flags before the ticket ID:

    kontora workflow-recover --execution-id EXECUTION_ID --revision N TICKET_ID

    workflow-recover acknowledges termination for the execution identity and revision the operator inspected. Before acknowledgement:

    1. Read current graph_state and the pause reason.
    2. Inspect invocation journals, saved results, processes and the worktree, including dirty files and interrupted Git operations.
    3. Establish that the previous executable stopped. A missing tmux window is not proof that detached descendants stopped.
    4. Submit the inspected execution ID and revision. If either changed, inspect the new state rather than automatically repeating the request.

    Recovery does not launch work or reset loop counts. Use retry separately for an eligible executable visit. Ordinary retry preserves execution and visit identity, while each physical invocation gets a fresh invocation ID. Restart creates a new execution identity. Neither operation erases old history.

    skip and set-stage are refused for graphs, including stopped graphs. Graph annotations and Plannotator rework are deferred and refused. Upgrade all CLI and daemon binaries sharing config or tickets together. Recovery does not promise exactly-once shell or hook effects, host-power-loss durability, or containment of arbitrary detached processes.

    kontora cancel TICKET_ID / kontora done TICKET_ID¶

    Move the ticket to cancelled or done. The daemon stops any running agent and removes a clean worktree, but preserves uncommitted changes. The branch remains. Neither command commits or merges changes.

    kontora move TICKET_ID STATUS¶

    The general form of the three above: moves a ticket to any status the config allows, which is the only way to reach human_review or a custom status from statuses: on the command line. Valid values are open, todo, paused, human_review, done, cancelled, plus any custom status. archived is deliberately excluded — see kontora archive.

    kontora skip TICKET_ID¶

    Legacy list pipelines only; graph skip is refused. Intermediate skip sets the next stage to todo. Daemon/API skip queues dependency-ready work even with auto_pick_up: false. Disk-only skip does not enqueue; use kontora run TICKET_ID afterward when automatic pickup is off. Final skip marks the ticket done without recording a successful run.

    If an agent is running, use kontora pause TICKET_ID first. Wait for the agent to stop before using skip. An active Plannotator review also blocks stage changes; close the review first.

    kontora set-stage TICKET_ID STAGE¶

    Legacy list pipelines only; graph set-stage is refused. Moves the ticket to a named stage of its pipeline. Leaves status and attempt unchanged; does not retry or queue the ticket. A ticket already in todo remains eligible for pickup.

    If an agent is running, pause the ticket first and wait for the agent to stop. Close any active Plannotator review before changing the stage. Use kontora retry TICKET_ID separately when you want to restart a paused ticket.

    The daemon can reject a stage change while teardown continues, even after status becomes paused. Disk-only CLI commands cannot observe daemon teardown; wait for termination before using them.

    kontora note TICKET_ID [TEXT] / kontora summary TICKET_ID [TEXT]¶

    Append a note, or set the ticket's summary. Positional text remains supported. Without text arguments, both commands read stdin and remove trailing LF characters.

    Prefer Pi's kontora_note({text: string}) and kontora_summary({text: string}) tools when available. Kontora's injected extension binds both tools to the current ticket, regardless of checkpoint settings. Tool restrictions still apply. Other agents and the dashboard assistant use stdin.

    Native tools reject blank text, embedded NUL, and text above 32,768 UTF-8 bytes. They pass text literally to the CLI without a shell. Native payloads appear in process arguments, so use stdin for large or process-list-sensitive text.

    For stdin submission, use a file-writing tool to create unique scratch files outside the repository. Submit the files with redirection:

    kontora note TICKET_ID < /absolute/path/note.md
kontora summary TICKET_ID < /absolute/path/summary.txt

    Replace TICKET_ID and each example path with the actual ticket ID and scratch path. Do not embed generated text in shell arguments or payload-bearing shell commands. Do not create the files with echo or printf. Redirection keeps shell syntax in the file from being evaluated.

    If a launched submission fails or lacks acknowledgement, its write outcome may be unknown. Read the ticket before resubmitting; do not retry or switch methods automatically.

    Notes trim surrounding whitespace and reject empty text. Adding or editing a note shifts headings outside fenced code only as needed to make the shallowest heading at least h3. Relative heading levels stay the same, capped at h6. Notes whose shallowest heading is h3 or deeper need no shift. Backtick and tilde fenced code stays unchanged; Kontora appends a closing fence if needed.

    Outside fenced code, a line beginning with # or ## at column zero ends the Notes section.

    Outside fenced code, only date-led bold-only lines or lines matching the full at · author · id grammar open notes. The first · field must start with YYYY-MM-DD for the date-led rule. The full grammar permits empty at and author fields, plus optional re:<id> and edited flags. Other bold text, such as **Verification:**, stays in the note. When adding or editing note text, Kontora stores byline-like bold lines with outer __ delimiters instead of **. Both render as bold.

    Existing tickets are not migrated. Full-body writes do not normalize note text. See Notes for the stored format.

    Summaries preserve spaces and internal newlines; the command does not force them onto one line or truncate them. At stage completion, the daemon captures the summary on the ticket and its history entry. Stage capture cuts text above 4,000 bytes at a UTF-8 boundary and appends \n[truncated]. A new stage clears the ticket's summary.

    Flag Description
    --author NAME Who the note is from. Defaults to $KONTORA_AGENT, which the daemon exports to every agent it spawns, and then to the config's author.
    --reply-to NOTE_ID The 4-character id of the note this replies to. One level only: replying to a reply is refused.

    These note flags must precede the ticket ID:

    kontora note --reply-to NOTE_ID TICKET_ID < /absolute/path/note.md

    kontora phase-complete TICKET_ID --completed TEXT --next TEXT¶

    Signals a boundary between two top-level ticket phases. Agents call it, not people. It appends one record to the sidecar named by KONTORA_CHECKPOINT_FILE and prints what the agent should do next; it reads no config and talks to no daemon.

    Flag Description
    --completed TEXT The phase that just finished, e.g. Phase 2: Expose the estimator. Required.
    --next TEXT The phase to begin next. Required.

    The daemon sets KONTORA_CHECKPOINT_FILE only for runs whose agent has a positive checkpoint_compaction_tokens. Without it the command records nothing, prints that checkpoint compaction is off for the run, and exits 0, so an agent that calls it in an unrelated run is not derailed.

    Relations¶

    A ticket carries two relation lists in its frontmatter. deps names the tickets it waits on, and the daemon will not run it until every one of them is human_review, done, cancelled, archived, or legacy closed. See dependency-aware scheduling. links is a symmetric "related" list that means nothing to the scheduler.

    All four verbs reject a missing ID and a ticket related to itself, and leave every file unchanged when they do. Repeating a call that has nothing left to do succeeds and writes nothing.

    kontora dep TICKET_ID DEPENDENCY_ID¶

    Makes TICKET_ID wait on DEPENDENCY_ID. Only the dependent ticket is written; the reverse edge is derived when it is read. A dependency that would close a cycle is rejected, and the error names the cycle.

    kontora undep TICKET_ID DEPENDENCY_ID¶

    Drops the dependency edge.

    kontora link TICKET_ID TICKET_ID...¶

    Relates the first ticket to each of the others. It does not relate the others to each other.

    Both sides of a link are written, and two markdown files cannot be written together. If the second write fails, the error names both tickets and says which one was already changed; running the same command again repairs the missing side.

    kontora unlink TICKET_ID TICKET_ID...¶

    Removes the relation between the first ticket and each of the others, on both sides.

    kontora archive --days N¶

    Marks every done or cancelled ticket whose file has not been modified for at least N days as archived, which hides it everywhere while keeping the file. --days is required and must be positive. Local only.

    Flag Description
    --days N Required. Age threshold in days, measured on the file's modification time.
    --dry-run List what would be archived and write nothing.
    --path PATH Only archive tickets for this repository path.
    --project NAME The same, by configured project name.
    --status STATUS Only archive one of done, cancelled or closed.
    -y, --yes Skip the confirmation prompt. Required when stdin is not a terminal.

    Each ticket the sweep archives records archived_from (the closed status it held), archived_at, and archived_by: sweep. The web UI writes the same three when a ticket is archived by hand, so a swept ticket restores from its Archive view the same way.

    Inspecting a run¶

    kontora logs [--stage NAME] TICKET_ID¶

    Prints the agent's log. Without --stage it shows the most recent one, falling back to the ticket's run history when there are no log files. Goes through the pager when one is set and stdout is a terminal.

    kontora activity [--stage NAME] [--run N] TICKET_ID¶

    Prints one stage run's structured transcript: the agent's messages and tool calls, one per line. Falls back to the plaintext log for agents that write no session record. Needs a running daemon. Goes through the pager when one is set and stdout is a terminal.

    kontora sessions [flags] TICKET_ID¶

    Prints the files behind the ticket's runs: by default the agent's own session JSONL, which is the transcript another tool would read. One row per history row, in history order, then the files no row claims.

    Flag Description
    --stage NAME Only this stage, and the annotation runs that borrowed its name.
    --run N Only this run number within the stage. Drops the stage log and the unattributed files, neither of which has a run number.
    --logs Print the stage log paths in place of the session files. Combines with --events.
    --events Print the activity sidecar paths in place of the session files. Combines with --logs.
    --all Print all three for every run.

    The columns are stage, run, artifact, path, and, when there is something to say about the row, a reason or a note. The path column holds - when nothing on this machine matches, so a fourth-field filter in awk gives the files that exist. In the run column, - marks the stage log, which is per stage, and ? marks a file no run claims, including the session of the stage running now.

    plan       0  session  /Users/a/.claude/projects/-Users-a-projects-kontora/2f1e0c7a-….jsonl
implement  0  session  /Users/a/.kontora/logs/kon-q88f/pi-sessions/implement/01JC9….jsonl
implement  1  session  /Users/a/.kontora/logs/kon-q88f/pi-sessions/implement/01JC9….jsonl  resumed: same file as run 0
implement  2  session  -  no session recorded (run predates session_ref)
review     0  session  -  session file missing: no /Users/a/.claude/projects/*/9a2c….jsonl
ship       0  session  -  agent "shell-runner" writes no session

    Three things worth knowing about the rows:

    • A resumed run shares its file with the run it continued. Claude's --resume and pi's --session both append to the existing JSONL, so one file can back several runs. The second row above says so rather than pretending the run has a file of its own.
    • A run that predates the session_ref field cannot be resolved back. For those tickets the command falls back to what is still on disk: a Claude stage's last run is recovered from its session record, and a pi stage's transcripts are listed with ? in the run column, because nothing says which file belongs to which run. The rest of such a ticket is gone for good: Claude runs other than the last of each stage, the run each pi file belongs to, and any run by an agent that is neither Claude nor pi.
    • A run is never dropped. A row with no path prints the reason instead, because a missing row reads as "this stage never ran".

    --logs prints one row per stage, not per run: every run of a stage overwrites <stage>.log, so it only ever holds the newest one. --events is per run.

    Local only. Every path names a file on the machine that runs the command. In remote mode the daemon's path either does not exist here or, if the caller runs kontora too, holds another ticket's bytes.

    kontora changes TICKET_ID¶

    Prints the commits on the ticket's branch and the per-file line counts against its base. Needs a running daemon. Uncommitted and untracked files are not included; inspect them in the ticket's worktree.

    kontora stats [flags]¶

    Prints the figures the dashboard's Stats page shows: throughput, median cycle time, first-pass rate, and per-stage, per-agent and per-project breakdowns. Needs a running daemon.

    Flag Description
    --range RANGE 1d, 1w, 30d, 90d or all. Defaults to 90d.
    --project NAME Only count tickets for this configured project.
    --pipeline NAME Only count tickets for this pipeline.

    Automations¶

    kontora automation manages scheduled agents through the daemon API. It does not create tickets. Every operation needs a running daemon, including local reads and schedule preview. There is no offline fallback to runtime storage. An explicit --url works without a local configuration file. Parent and child help work offline: kontora automation -h and kontora automation update -h.

    Every child accepts --config PATH, --url URL, --token TOKEN, and --operator-token TOKEN. The credentials default to KONTORA_TOKEN and KONTORA_OPERATOR_TOKEN, respectively. The client sends bearer and operator credentials independently for HTTP and terminal connections. Automation commands do not accept --tickets-dir.

    REF is a full automation ID (aut- followed by 32 lowercase hexadecimal characters) or an exact configuration key. Display names and abbreviated IDs are not accepted. Keys resolve through the active definition list, without ticket lookup. For retained history after deletion, use the original full ID. A recreated key identifies a different definition.

    Every child except interactive attach accepts --json. JSON stdout contains API objects, without status prose or request diagnostics. List and history output preserve availability and pagination envelopes. Empty collections remain []; unknown cost and statistics remain null. ls --json prints the availability envelope when HTTP 200 reports unavailable storage. The CLI explains the error on stderr and exits nonzero. HTTP errors produce diagnostics and a nonzero exit without JSON stdout. Human output distinguishes disabled scheduling from a run's execution phase and unknown cost from zero.

    kontora automation ls [flags]¶

    List definitions in key order, including their full IDs, scheduling state, run phase, schedule, timezone, agent, and last outcome.

    Flag Description
    --state STATE all (default), enabled, or paused.
    --query TEXT Case-insensitive substring across searchable definition fields.
    --project NAME Exact configured project filter.
    --agent NAME Exact agent filter.

    kontora automation view REF [flags]¶

    Show the complete specification and prompt, revision, schedule, current and last runs, statistics, and cost coverage.

    kontora automation new [flags]¶

    Create a definition in the daemon's YAML configuration. Scheduling defaults to disabled. Read the prompt from a local file or stdin with --prompt-file -.

    kontora automation new \
  --name "Morning repository report" \
  --prompt-file ./report-prompt.md \
  --path /srv/projects/app \
  --agent claude \
  --schedule "0 9 * * 1-5" \
  --timezone Europe/Berlin
    Flag Description
    --name NAME Required display name.
    --prompt-file FILE Required local file containing the Go prompt template; - reads stdin.
    --path PATH Required repository path on the daemon host.
    --agent NAME Required configured agent name.
    --schedule SCHEDULE Required numeric five-field cron or whole-minute interval, such as 30m. Minimum: 1m.
    --key KEY Lowercase kebab-case configuration key. Derived from the name when omitted.
    --model MODEL Optional model override for a supported agent.
    --timezone ZONE IANA timezone; defaults to UTC.
    --workspace MODE worktree (default) or repo.
    --overlap POLICY skip (default), queue, or replace. Queue keeps one pending run.
    --timeout DURATION Positive run timeout; defaults to 30m.
    --enabled Enable scheduling; defaults to false. Use --enabled=false to set false explicitly.
    --request-id ID Stable request identity for retries. Generated once when omitted.

    kontora automation update REF [flags]¶

    Change only explicitly supplied fields. The CLI fetches the definition, merges your changes, and submits the complete specification. Accepts all specification flags from new except --key: --name, --prompt-file, --path, --agent, --model, --schedule, --timezone, --workspace, --overlap, --timeout, and --enabled. At least one field is required. --model '' clears the override; --enabled=false disables scheduling. The key is immutable. Update does not accept --request-id.

    --revision N sets a positive expected revision. Without it, the CLI uses the fetched definition's revision. Delete, pause, and resume use the same revision policy. A stale revision fails without an automatic retry or overwrite. Inspect the current definition before deciding whether to repeat the change.

    kontora automation update morning-report --model '' --enabled=false
kontora automation update morning-report --prompt-file - < ./revised-prompt.md

    kontora automation duplicate REF [flags]¶

    Copy the specification into a new definition. Scheduling defaults to disabled, even if the source is enabled. Accepts --name NAME, --key KEY, --enabled, and --request-id ID. The default name is <name> (copy); the server derives the key when omitted. Retry with unchanged source inputs and the same request ID. Changed inputs under that identity must remain a conflict.

    kontora automation delete REF --yes [flags]¶

    Delete the definition and request termination of unfinished work. Historical runs and logs remain. --yes or -f is required before any deletion request. Accepts --revision N. JSON confirmation contains the resolved id and deleted status.

    kontora automation pause REF [flags]¶

    Disable future scheduling without cancelling accepted runs. Manual runs remain available while paused. Accepts --revision N.

    kontora automation resume REF [flags]¶

    Enable scheduling from a future slot, without replaying paused time. Accepts --revision N.

    kontora automation run REF [flags]¶

    Request a manual run, including while paused. Accepts --request-id ID. The returned phase, outcome, and result describe the accepted request, not proof of completion. Overlap policy can queue or skip the request.

    Creation, duplication, and manual runs print a request ID to stderr before sending. Manual runs also print the resolved full automation ID. After an uncertain response, keep that identity pair and repeat with the same request ID. The CLI does not retry mutations automatically. An explicit --request-id on run requires the original full automation ID, never a key. This prevents a retry from launching a recreated definition with the same key.

    kontora automation run aut-0123456789abcdef0123456789abcdef --request-id report-2026-11-11

    kontora automation stop REF --run N [flags]¶

    Request termination of the specified positive run number. The command never switches to another current run. A returned stopping or recovery_required phase does not prove termination. Inspect the returned phase and outcome.

    kontora automation runs REF [flags]¶

    Read one page of history. --offset N defaults to 0; --limit N defaults to 20 and accepts 1 through 200. Rows include run number, trigger, phase, outcome, timestamps, result, exit codes, and nullable cost. New runs can shift offset pages; pagination does not promise a snapshot. Use the original full ID for a deleted definition.

    kontora automation logs REF --run N [flags]¶

    Read composed logs for a positive run number. Human output includes timestamp, source, kind, and text. --json prints structured logs. --raw prints the endpoint's text unchanged, without styling, paging, or status prose. --raw and --json are mutually exclusive. Raw logs are composed text, not the original terminal capture. Use the original full ID to read retained logs after deletion.

    kontora automation preview --schedule VALUE [flags]¶

    Show the server's schedule description and four future occurrences, using the daemon's clock. --timezone ZONE defaults to UTC. Preview does not change configuration and has no offline mode.

    kontora automation preview --schedule '0 9 * * 1-5' --timezone Europe/Berlin

    kontora automation terminal REF --run N [flags]¶

    Inspect server-resolved terminal metadata for a positive run number. The server controls terminal eligibility and identity checks. This command does not attach or construct a local tmux target.

    kontora automation attach REF [flags]¶

    Attach read-only to the current run. --run N selects an exact positive run number; --rw enables input. With --run, the client does not require a live definition, so retained IDs can reach eligible terminals after deletion. The daemon resolves and verifies the saved terminal target. Queued, completed, or unavailable runs have no attachable terminal. This command is interactive and has no --json flag.

    See Automations for results, overlap, and recovery.

    kontora attach [--rw] TICKET_ID¶

    Attaches to the running ticket's terminal: the tmux window locally, a WebSocket to the daemon in remote mode. Read-only unless --rw is given. Locally, omitting the ticket ID opens a picker of running sessions.

    kontora attach [--rw] AUTOMATION_ID attaches to the automation's current run using its full ID (aut- followed by 32 lowercase hexadecimal characters). The daemon resolves and verifies the saved terminal target. Arbitrary session names are not accepted. A queued, completed, or unavailable run has no attachable terminal. Top-level attach also accepts --operator-token TOKEN, defaulting to KONTORA_OPERATOR_TOKEN. Use kontora automation attach REF --run N to select an exact run or use a configuration key.

    kontora review TICKET_ID / kontora annotate TICKET_ID¶

    For graph tickets, annotate is refused. review can show the diff, but feedback cannot start automatic rework. For eligible tickets, open the diff or markdown in Plannotator. The daemon spawns the binary, so in remote mode the window opens on the daemon host, not on the caller's screen. review needs the ticket to be in human_review.

    Supervised results¶

    kontora result [--input-file /absolute/path/result.json] TICKET_ID¶

    Submit the current invocation's terminal result. Without --input-file, read JSON from stdin. Put flags before the ticket ID. This command requires daemon-supplied invocation context; outside a bound invocation it fails rather than succeeding as a no-op. Do not set these variables yourself or use another invocation's context. The daemon binds result variables after configured agent environment merging.

    {
  "outcome": "blocked",
  "summary": "Required native-device evidence is unavailable.",
  "next_step": "Provide device access or explicitly change the proof-first requirement."
}

    Version 1 accepts only outcome, summary, and optional next_step. Graph agent nodes use version 2 and additionally accept verdict. A complete result must include a declared verdict when the node defines verdicts; undeclared verdicts are refused. For example:

    {"outcome":"complete","summary":"Review found required fixes","verdict":"changes_requested"}

    This completes the review node; it does not mean the ticket is accepted. A condition can compare the verdict and follow an explicit rework loop. Graph agent nodes always require results, independently of epic membership. Check nodes use observed process exit codes rather than agent result submission. Invocation, workflow execution, visit and fingerprint identity come from daemon-bound context, never user payload fields.

    For both versions, outcome is complete or blocked; summary must be nonblank, and blocked requires a nonblank next_step. All fields are strings. Payloads must be valid UTF-8 JSON, at most 32 KiB, with no NULs, duplicate or unknown fields, or trailing content. Incompatible context versions are rejected. Invocation identity is not a payload field. Use a file-writing tool to create a unique scratch file outside the repo, then submit it; do not interpolate generated JSON into shell commands.

    Pi also exposes kontora_result({outcome, summary, next_step?, verdict?}), independently of checkpoint compaction. It submits through the CLI without a shell and checks the acknowledgement. Check acknowledgement with either transport: identical resubmission is idempotent; a conflicting submission cannot replace the first result. A late result cannot finalize a replacement invocation. Notes, summaries, final prose, question markers, and phase checkpoints are not terminal results.

    Activated epic supervisors and their children, including rework, must report. Non-graph passive-epic children and unrelated tickets, annotations, and assistant-only runs retain their existing result requirements. complete means the assigned current stage is complete, not the whole ticket or human acceptance. Review completion can still leave fixes for later stages. Fixture work is not complete if the stage still requires production foundations or other acceptance evidence.

    blocked, or a missing/invalid result after a clean supervised run, pauses the same stage without consuming a retry or deleting the worktree. It does not enter pipeline retry or back policies. A complete report cannot override execution or provider failures, hooks, or epic child validation. The daemon owns lifecycle transitions; do not mark your own ticket done. See recovery for interrupted runs and local authority for escalation.

    Upgrade the CLI and daemon together. Verify effective Pi/Claude instructions before enabling autonomous local commits. Do not use rollout to restart live epics or migrate existing ticket state.

    Analysis¶

    kontora estimate-compaction [flags]¶

    Projects token savings from checkpoint compaction by replaying completed Pi session traces. Read-only: it scans JSONL files and writes nothing. Local only.

    Flag Description
    --logs-dir PATH Path to the logs directory. Defaults to the config's logs_dir. When provided, the config file is not required.
    --stage NAME Pipeline stage to analyze. Defaults to implement.
    --thresholds LIST Comma-separated token thresholds to evaluate, e.g. 100000,150000,200000. Defaults to 100000,125000,150000,200000,250000.
    --top N Number of top sessions to include in the report. Defaults to 20.

    The report includes:

    • Coverage includes scanned and eligible sessions. It also counts branch_summary, no_usage, unreadable, broken_chain, has_compaction, and live_resume exclusions. A session is treated as live when a resume marker identifies it or its latest recorded activity is less than 15 minutes old. This check uses timestamps inside the JSONL, so copying old sessions does not mark them as live.
    • Calibration shows the summary ratio, summary output tokens, and post-compaction context. Each statistic includes its sample count and low, median, and high values. Without a usable post-compaction sample, the report prints no token-reduction figures.
    • Scenarios show projected compaction counts and raw-token reductions for CAL P25, CAL P50, and CAL P75. These labels are calibration percentiles, not reduction bounds. CAL P25 uses smaller summaries and post-compaction contexts and usually projects the largest reduction; CAL P75 uses larger values and usually projects the smallest. The scenarios replay the recorded call sequence. They do not predict changed agent behavior.
    • Top sessions rank session files by projected median raw-token reduction at the lowest requested threshold. Each row includes the ticket, stage, and session filename so retries remain distinguishable.
    • Limits state why the report does not estimate implementation quality or cost. They cover changed tool calls, cache identity, and pricing.

    Example:

    kontora estimate-compaction \
  --stage implement \
  --thresholds 100000,125000,150000,200000,250000 \
  --top 20

    kontora start [flags]¶

    Runs the daemon in the foreground. Only one instance per config directory: a second one exits on the file lock. Local only.

    Flag Description
    --address HOST Web server listen address, overriding web.host.

    kontora setup [--agent]¶

    Writes the config file. Plain setup runs an interactive wizard. setup --agent prints a brief for a coding agent to follow and writes nothing itself; the brief is embedded in the binary, so it describes the schema the installed version accepts. Local only.

    kontora doctor¶

    Checks the config, the required tools (git, tmux), each agent binary, each configured project's repository, Plannotator, and the web port. Exits non-zero when a hard prerequisite fails; missing directories and an occupied port are warnings. Local only.

    config prints the effective configuration with defaults applied, with web.token replaced by a placeholder. In remote mode it prints the daemon's pipelines, agents, and custom statuses instead.

    Utilities¶

    kontora fmt¶

    Reads Claude Code stream-json on stdin and prints it as readable text. Takes no flags and talks to nothing, so it works with KONTORA_URL set.

    kontora skills¶

    Prints the agent-facing reference topics embedded in the binary: cli, tickets, pipelines and config. They are written for an agent driving Kontora from a shell, flags and arguments first, and cover the same ground as this site in a shorter form. Reads neither the config file nor the ticket store, so it answers in remote mode and before kontora setup.

    kontora skills list                 # the topics, one line each
kontora skills list cli             # that topic's section headings
kontora skills show tickets         # the whole topic as markdown
kontora skills show cli new         # one section of it

    The section argument matches a ## or ### heading: exactly first, then as a unique case-insensitive substring, so show cli new prints ## kontora new. An ambiguous name prints the candidates and exits 1, as does an unknown topic.

    kontora completion <shell>¶

    Prints a completion script for bash, fish or zsh. Each one completes the verbs, their flags, and, for the verbs that take one, a ticket ID. The ID list comes from kontora ls --closed, so closed tickets are offered too.

    kontora completion fish > ~/.config/fish/completions/kontora.fish
kontora completion zsh  > ~/.zsh/completions/_kontora   # dir must be in $fpath before compinit
kontora completion bash > ~/.local/share/bash-completion/completions/kontora

    See Shell completions for the per-shell install steps.

    kontora version¶

    Prints the version.

    Remote mode¶

    Setting --url or KONTORA_URL points every client command at a daemon over HTTP instead of the local files. See Remote access for daemon-side setup.

    Supported: ls, view, new, init, update, delete, run, schedule, pause, retry, cancel, done, move, skip, set-stage, note, summary, dep, undep, link, unlink, logs, activity, changes, stats, all automation children, review, annotate, config, attach.

    Rejected, because they act on local files: edit, search, archive, estimate-compaction, sessions, doctor, start, setup.

    Unaffected, because they touch neither the daemon nor a config file: fmt, skills, completion, version, help, phase-complete.

    Paths passed to --path name locations on the daemon host, not on the caller's machine.
